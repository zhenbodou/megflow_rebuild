# 第 9 课：性能、兼容性与发布维护

能维护宏意味着用户改一个字段、升级编译器或更换目标平台时，你知道该检查什么。本课把这些要求变成可执行的工作方法。

## 1. 按失败层次组织测试

| 测试层 | 输入 | 真正证明什么 |
| --- | --- | --- |
| 解析器单元测试 | 合法/非法 token | 语法规则、错误收集符合设计 |
| AST 检查 | 生成 token 再 parse2 | 输出是可解析的语法，不证明类型正确 |
| 下游成功编译 | 泛型、路径、属性组合 | 编译器接受实际调用方式 |
| trybuild 失败用例 | 用户错误程序 | 因预期理由失败、位置与说明可读 |
| 运行测试 | 业务输入、失败路径 | 求值次数、消息与清理行为正确 |

不要用字符串包含 `where` 的断言代替泛型编译测试。也不要只让错误用例“随便失败”：缺依赖和真正的属性错误都能使编译失败，但只有后者是我们想验证的。

本书自动检查入口是 `scripts/check_macro_course.py`；引擎宏负例另由 `cargo test --manifest-path code/Cargo.toml -p flow-derive --test ui --locked` 验证。新增语法时，同时写一个合法例和一个最接近的非法例。

## 2. crate 选型与学习顺序

| 工具 | 解决的问题 | 学习与使用边界 |
| --- | --- | --- |
| proc_macro | 编译器传入/接收 token | 标准库，无需 Cargo 依赖；入口使用 |
| proc-macro2 | 可在普通程序操作 token、span | 第 4 课；不提供类型推导 |
| syn | Rust AST、自定义 Parse、属性解析 | 第 4、6 课；按需要开 feature |
| quote | 插值、重复、ToTokens、quote_spanned | 第 4、6 课；不自动保证类型正确 |
| trybuild | 编译成功/失败回归 | 第 8 课；预期诊断要人工审阅 |
| inventory | 分散登记后统一枚举 | 第 10 课；不是 syn 的替代品 |
| proc-macro-crate | Cargo 依赖名字定位 | 第 7 课；仍需下游改名测试 |
| darling | 将辅助属性解析成结构化配置 | 选学；先会 syn 的手工解析，理解自动派生省去什么 |
| prettyplease | 格式化 syn 文件 AST，便于阅读 | 选学；仅改变展示，不能验证卫生性和类型 |
| cargo-expand | 展示编译器展开结果 | CLI，不是业务依赖；结果是诊断辅助 |

可查阅 [darling](https://docs.rs/darling/latest/darling/)、[prettyplease](https://docs.rs/prettyplease/latest/prettyplease/) 和 [cargo-expand](https://github.com/dtolnay/cargo-expand) 的官方说明。后四项选学工具没有加入本工程依赖，阅读 API 时先确认它们支持的 syn 主版本，不能把最新示例直接混到本书锁定的 syn 2 工程。

实践选型题：只有 skip/rename 两个选项时继续手工 parse_nested_meta；若配置有多层嵌套、默认值与多种接收对象，再评估 darling。判断依据是减少重复且保持诊断质量，不是依赖越多越专业。

## 3. 编译性能从测量开始

过程宏在构建时执行；生成的代码又要被编译。慢可能来自解析器，也可能来自生成了过多 impl 或复杂泛型。先建立相同工具链、相同输入规模的基线，再比较。

```bash
cargo build --manifest-path code/macro-labs/Cargo.toml --timings --locked
```

记录冷构建和增量构建时缓存条件；不要把已有缓存的第二次构建拿来证明优化。逐步增加字段或调用数，观察增长趋势；发现 TT muncher 尾部重复匹配开销后，可改成直接重复或 syn 解析。

避免对同一 AST 反复 stringify 再 parse，也避免只为格式化输出引入庞大运行依赖。没有测量结果前，不给出“快了几倍”的结论。

## 4. 确定性、主机与目标

过程宏运行在编译主机上，生成代码将在目标平台编译和运行。因此在宏实现中用 `cfg!(target_os = ...)` 判断的是宏自身编译目标，交叉编译时通常不是业务程序目标。需要目标条件时，生成目标侧 `#[cfg(...)]` 并在目标编译测试中验证。

不要靠全局计数器决定公共生成名称，也不要让文件系统遍历顺序决定端口编号。声明顺序或显式排序才是可解释的协议。文件、环境和网络输入会影响可重复构建与增量追踪；优先使用显式 token 配置。过程宏具备编译进程的能力，使用依赖时应理解其执行发生在构建期间。

## 5. 宏的公共接口不止函数签名

支持的语法、辅助属性、生成方法、trait 约束和默认行为都是接口。以下改动都需要评估兼容性：新增保留字段名、改变重复项规则、让过去合法的泛型要求额外 trait、调整属性顺序、改变生成路径或注册顺序假设。

诊断快照改变不一定表示语义破坏，但仍应审核。保持工具链版本可重复；升级时先分别运行旧/新版本测试，再决定哪些 stderr 变化合理。MSRV 是承诺的最低 Rust 版本，需要在该版本真实编译，而不是根据 edition 猜测。

发布前本地检查的顺序是：格式 → 单元和下游测试 → feature/目标/MSRV 矩阵 → 文档和示例 → 打包检查。可用 `cargo package --list` 检查文件是否包含，但独立课程中的 path 依赖并不是可直接发布的产品配置；发布时要给依赖设计真实版本与顺序。不要执行真实发布来代替 dry-run 验证。

## 专家练习：提交一份设计说明

为 Describe 的下一版填写：新语法是什么、旧调用是否受影响、生成代码是什么、非法输入指向哪里、是否支持 enum/no_std/改名依赖、增加哪几项测试、编译成本如何测量。

参考判断：若支持 enum，必须覆盖具名、元组、单元 variant 和泛型字段；若支持 no_std，要处理 alloc 并建立独立下游；若支持依赖改名，要确保测试中没有原名依赖兜底。没有证据的能力应写“未验证”，不能写“完全支持”。
