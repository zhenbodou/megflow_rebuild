# Ch5.3 全景回顾与完整框架毕业验收

本书的最终目标是：你从空工程逐步开发，读完时已拥有功能和业务逻辑对齐原版 Rust 部分的
MegFlow，并能解释、修改和独立维护它。当前仓库仍处于实现与教学补全阶段，不能用一个
可运行核心子集代替这个目标。本章记录如何证明完成，不把缺失功能改称可选进阶。

最新缺口与已验证证据见 [完整重构验收账本](../part0/ch04-completeness-audit.md)。
测试数量会随开发变化，因此不再把历史测试数或某次检查结果写成永久的毕业证明。

## 1. 从配置到结果，逐层解释自己的实现

先不看代码，沿下面的路径讲解一次：

```mermaid
flowchart LR
    A[配置文本] --> B[解析与配置处理]
    B --> C[查询节点及端口声明]
    C --> D[验证连接与选择消息类型]
    D --> E[创建通道并构造节点]
    E --> F[任务调度与消息处理]
    F --> G[关闭、错误与资源收尾]
```

当前工程已有这条路径的若干可运行场景，包括命名接线、类型化端点与直接转换。
但配置处理不能等同于 serde 解析，任务调度不能等同于调用 spawn，静态压平也不能
等同于原版完整子图运行时。每个方框都需要进一步展开为明确的行为与测试。

练习时给每条箭头说出三个信息：传递的 Rust 类型是什么；谁拥有其中的数据；失败如何
返回或传播。如果你只能说“下一步调用这个函数”，仍需要回到相应实作章完成实验。

## 2. 已有知识如何支撑独立开发

| 知识 | 你应能独立完成的任务 | 学习位置 |
| --- | --- | --- |
| 所有权、借用、生命周期 | 解释配置引用借自哪里、端点何时释放 | Ch1.1、Ch3.1、Ch3.2a |
| 泛型、trait、dyn、Any | 将不同节点放入同一集合，安全取回载荷类型 | Ch1.2、Ch1.3、Ch2.1a |
| async、Future、Tokio | 构造背压实验，判断取消时消息是否已经出队 | Ch1.4a、Ch1.4b、Ch1.4e |
| 类型描述与转换 | 推导队列类型，保留转换前后的消息上下文 | Ch1.4c、Ch1.4d、Ch3.2a |
| 声明宏与过程宏 | 先手写目标代码，再解析、生成、测试宏 | 宏专题第 1—10 课 |
| 函数指针与注册 | 不创建节点就取得构造器和端口元信息 | Ch2.4b、宏专题第 10 课 |
| serde 与配置验证 | 区分字段错误、引用错误和业务参数错误 | Ch3.1a |
| 共享状态与同步 | 判断 Arc 是否足够，选择锁或原子操作 | Ch4.3 |
| 递归与调用路径 | 区分子图兄弟复用和祖先引用环 | Ch4.4a |

这张表是练习要求，不是保证“看过就掌握”。每项至少要完成一次改变输入条件的实验，
并预测结果。例如使用减法验证端口顺序，使用不同 partial_id 验证元信息来自正确输入。

## 3. 仍需完成的 Rust 能力不能留给读者自行补课

下面是后续必须补齐的实现与教学主线。路径均相对于父目录原版 `../megflow`。
这不是完整文件清单；验收账本还需按实际源码继续细分。

| 必做主线 | 原版入口 | 完成所需证据 |
| --- | --- | --- |
| 完整通道协议 | flow-rs/src/channel/ | ChannelStorage、计数、关闭、flush/epoch、克隆及转换的联合行为 |
| 完整节点与宏协议 | flow-derive/src/、flow-rs/src/node/ | 模板、数组/字典/动态端口、方法适配、诊断及下游兼容性 |
| 完整配置处理 | flow-rs/src/config/ | 预处理、跨连接类型推断、优化及配置错误边界的对照 |
| 嵌套、共享与动态子图 | flow-rs/src/graph/、broker.rs | 实例创建与销毁、路由、容量、资源作用域和生命周期 |
| 运行时与任务管理 | flow-rs/src/rt/ | 本地任务池、线程固定、阻塞任务、错误与停止行为 |
| 算法消息结构 | flow-message/src/algo_base/ | Frame、Image、Item 等 Rust 数据与操作语义 |
| Rust 业务插件 | flow-plugins/src/ | 相关字节、图像、视频及业务管线功能的实际输入输出 |
| 调试、图输出与性能信息 | flow-rs/src/debug/、profile/、config/graphviz.rs | 协议、统计结果、图表示及可观测行为 |

每条主线都要有“为什么需要 → 最小手写实现 → 用到的 Rust/crate → 完整实现 → 错误实验
→ 原版对照 → 独立验收”的教学链。只给源码目录、说它很复杂或建议读者以后再研究，
不满足本书的完整教学目标。

“纯 Rust”需要逐项辨认运行路径：Python 节点执行不是用 Rust 业务节点替代的同义词，
原版调用外部库的 Rust 功能也不能因依赖难获得就删除。对于确实不能运行的外部依赖，
需要记录可验证接口、缺失证据及替代实现的语义要求，不能悄悄缩小验收范围。

## 4. 完成的两条验收线

**实现验收**检查功能与业务行为。为原版每项 Rust 功能列出输入、输出、状态变化、失败
条件和资源生命周期；采用有区分能力的对照案例。结果数字相同不足以证明序号、权重、
顺序、共享状态、停止时机和错误传播相同。

**教学验收**检查从空目录能否完成它。记录每章新增/修改的文件和依赖，保证示例不会
调用后续才出现的模块；阶段检查点能够独立编译运行。最终源码只是答案参考，不能替代
逐步开发路径。所有涉及的 crate 都要说明用途、关键 API、版本边界及常见错误。

这两条验收都完成，才能说“读完后框架已经开发出来”。一个功能已经写在参考工程里，
但没有教会读者如何构造，教学验收仍未完成；一章讲得清楚但只实现了简化语义，实现验收
仍未完成。

## 5. 怎样使用自动检查

在仓库根目录运行核心回归与书籍检查：

```sh
cargo test --manifest-path code/Cargo.toml --workspace --locked
mdbook build book
python3 scripts/check_book_links.py
```

独立消息、异步、配置、手写节点和宏检查点还有各自脚本，见 Ch0.5 及对应实作章。
必须先检查脚本验证的范围，不能把工作区测试通过当成所有阶段都能从空工程复现。

结果需要带上下文记录：验证哪个提交、用什么命令、覆盖哪个要求、还有哪些未覆盖。
链接检查通过只证明本地跳转和直接引用资源存在；mdBook 构建通过不代表所有忽略编译的
代码块可运行；某个配置成功不代表原版的全部配置字段已支持。

当前工具可能报告预处理器与 mdBook 的版本警告，应如实记录。没有运行的 clippy、格式
检查或远端部署，不得写成“全部干净”或“发布成功”。

## 6. 最终独立开发考核

最终版本的读者应能完成以下任务，并解释自己的设计：

1. 从空目录建立工程，按章节依次实现消息、通道、节点、宏、注册和配置处理。
2. 手写一个保留元信息的节点，再用自己实现的宏替换样板，比较展开代码和行为。
3. 构造包含类型转换、多消费者、数组端口和资源的图，验证数据与关闭行为。
4. 完成嵌套、共享、动态子图和完整控制协议，重现原版相应场景。
5. 接入要求范围内的算法消息及 Rust 业务插件，验证正常、边界与错误输入。
6. 修改一种业务行为，补出能区分新旧结果的测试，定位到具体代码与知识点。

这些是本书继续完善时必须兑现的毕业要求，当前不能宣称全部可完成。后续新增章节与
实现应直接服务这些要求，直到两条验收线都有足够证据，再将本章更新为正式完成记录。
