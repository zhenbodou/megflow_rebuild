# Ch0.5 怎样从“看懂代码”走到“自己写出框架”

本书的最终验收不是代码文件存在，也不是测试数量多，而是你能解释每层设计的原因，
从空目录逐步写出它，遇到错误能定位，并用业务结果证明重构与原版一致。
当前书中仍有省略步骤和只展示终点的章节，验收账本会继续跟踪，不能把它们算作教学完成。

## 本书已经确定的交付方式

完整实现范围为 flow-rs、flow-derive、flow-message 和 flow-plugins。排除 Python/C
绑定、JavaScript 调试前端和 quickstart 工具，但保留 Rust 调试服务与服务插件。
允许重新设计公开 Rust API；配置、业务结果、状态、错误和资源生命周期必须按原版
可观察行为验收。私有依赖采用本地纯 Rust 等价实现，证据不足的行为继续标为未验证。

每章应完整展示本章新增或修改文件的内容，注明继承的前置工程、Cargo 配置、运行命令
和预期结果；不能只提供补丁或跳转到最终源码。全文展示仍要配合逐段讲解与独立构建，
并不能仅因源码被 include 到页面就视为读者已经能够按章复现。现有章节将逐步按此
标准整理，所有目标内缺项完成前不会把最后一章改成已毕业状态。

### 具体到一章，应该怎样边看边写

以 [Broker 章](../part4/ch08-broker.md) 为例：先建立书中给出的目录，输入 Cargo.toml、
lib.rs 和 error.rs；再按 State、Mailbox、端点、Broker 的顺序输入实现，阅读每一部分
的设计解释。最后输入 notify 示例和完整测试，运行书中的命令，与精确输出核对。

这与“下载最终工程后执行 cargo test”证明的事情不同：前者检查本章材料是否足以
独立构造模块，后者检查现有所有模块是否协作。两种检查都需要。学习到依赖不明的
类型时，应能在本章或明确指出的前置章节中找到它的定义，不能要求你猜测补齐。

本书修订时逐章使用以下清单：

| 检查 | 必须能在正文中找到 |
| --- | --- |
| 从哪里开始 | 前置章节、目录树、已存在文件与依赖 |
| 写哪些内容 | 本章新增或修改文件的完整内容，包括 Cargo 配置 |
| 为什么这样写 | 新需求、状态、所有权和控制流，而非仅逐行翻译语法 |
| crate 怎样使用 | feature、关键 API、输入输出、锁文件和错误处理 |
| 怎样运行 | 正确工作目录、完整命令、预期结果及首次下载说明 |
| 怎样判断写错 | 可重现错误及其原因、具体测试和修复位置 |
| 是否真正独立 | 不借用后续模块的新目录编译记录 |

Broker 独立实验目前已满足最后一项的模块级验证，但还不能证明整个章节序列累计
无缺口。后续修订要把这些模块级验证继续连接成整本书的累计工程路线。

## 1. 每个知识点要回答六个问题

以“为什么信封载荷是 Option”为例，不先背类型名，按下面的顺序学习：

| 问题 | 本例要回答的内容 |
| --- | --- |
| 为什么需要它？ | 取走载荷后，仍需要保留信封上的序号、地址等信息 |
| 最小例子是什么？ | 一个字段保存 Some(7)，take 后变为 None |
| Rust 怎样表达？ | `Option<T>` 表示有值/无值；&mut self 允许修改字段 |
| 在框架中放在哪里？ | Envelope 的载荷字段和 unpack/take 方法 |
| 写错会发生什么？ | 已取走的载荷再次 unpack 会失败；new 新信封可能丢元信息 |
| 怎样证明自己会了？ | 不看实现写一个改变载荷类型、保留序号的函数，并解释所有权去向 |

后续讲 Arc、Future、trait 对象、过程宏、配置和调度时，都应落实同一组问题。
只给术语定义或大段完整代码不够；代码前要先说目标，代码后要解释数据和控制流。

## 2. 知识的依赖顺序

先学到能完成当前任务，不要求一口气背完 Rust 标准库，但最终使用到的知识不能跳过。

| 开发阶段 | 必须先懂的 Rust | 必须能独立完成的作品 |
| --- | --- | --- |
| 消息 | struct、泛型、Option、所有权、借用、trait、Any | 载荷可变换但元信息不丢失的信封 |
| 通道 | Future、async/await、任务、Send、Arc、锁、关闭与背压 | 有界/无界收发，验证关闭与取消 |
| 手写节点 | trait、状态、循环、Result、? 的返回边界 | 不用宏的单节点生命周期 |
| 宏 | token、Parse、AST、quote、泛型、span、属性、crate 边界 | 为手写节点生成同等代码，验证非法输入 |
| 注册与配置 | 函数指针、静态数据、serde、集合、图结构 | 按配置找到节点并检查接线 |
| 运行时 | 并发任务、资源作用域、错误传播、收尾 | 正常/失败都能退出的多节点图 |
| 高级协议 | 状态机、轮次、寻址、共享与隔离 | flush、动态/共享子图和原版业务场景 |

## 3. 一个完整示范：为什么节点要处理信封

先不碰异步和宏。需求只有一句话：把整数 7 转成字符串 frame-7。
最直接的业务函数如下：

```rust

```

函数接收 u32，返回 String。format! 生成一个拥有自身存储的字符串。这里的 7 只是业务
数据，不携带消息序号。到这一步，根本不需要框架。

现在增加第二个需求：这条数据带有序号 42，处理完后下游还需要该序号。
仅仅返回 String 就不够，所以把载荷与元信息一起传入，并一起传出：

```rust,ignore
{{#include ../../../code/flow-message/examples/first_principles.rs:preserve_context}}
```

逐行读：

1. 参数按值接收 Envelope，函数拿到整个信封的所有权。调用后，上游不能继续使用这个变量。
2. mut 允许我们修改信封。unpack 取出载荷，原信封的载荷位置变成 None；元信息仍在。
3. 调用刚才独立的业务函数。业务逻辑本身不必知道序号、通道或调度器。
4. repack 把新 String 放进新类型的信封，同时保留原元信息。返回类型因此是 `Envelope<String>`。

不要用 Envelope::new(output) 代替最后一行：它会创建默认元信息，而不是继承序号 42。
这不是 Rust 语法错误，编译器不会替你发现；需要契约测试检查业务语义。

调用与验证：

```rust,ignore

```

`..Default::default()` 填补其余元信息字段；它不覆盖我们已经写出的 partial_id。
Some(42) 表示明确指定序号；None 表示没有指定。最后的 is_none 检查载荷已经取走，

## 4. 再增加一个需求：同一条管道承载不同消息类型

泛型 `Envelope<u32>` 和 `Envelope<String>` 是不同类型，不能直接作为同一个 Vec 的
元素类型。框架采用类型擦除，将它们封成统一的 SealedEnvelope，之后再安全恢复。

```rust,ignore
{{#include ../../../code/flow-message/examples/first_principles.rs:erased_payload}}
```

seal 把信封移进类型擦除容器，没有把 String 转成字节或 JSON。真实类型仍存在，
只是静态接口不再直接暴露它。downcast_ref 试认成错误类型时返回 None；
downcast_mut 认成正确类型后拿到可变借用，才可以 unpack 取出载荷。

这里先认识需求和可观察行为，trait 对象与 Any 的实现原理在 Ch1.2、Ch1.3 展开。
还解释不了 dyn、Box、生命周期或 Send 时，应回到对应章节，不靠背这几行代码跳过。

完整程序在 `code/flow-message/examples/first_principles.rs`，从仓库根目录运行：

```bash
cargo run --manifest-path code/Cargo.toml -p flow-message --example first_principles --locked
```

预期输出：`完成：业务转换、元信息保留、取出载荷、类型擦除与安全恢复`。
这只是消息层示范，不是完整框架。它展示一条原则：每加一层机制，先给出旧实现无法
满足的新需求，再解释新增代码。

## 5. 合上书后的练习

先自己写，失败后再看提示或参考方案。

**练习 A：** 将业务函数改为把 String 变成长度 usize，保留原信封序号。
提示：所有权进入函数后，先取出字符串，再计算长度，再 repack。
参考方案：`fn length(mut e: Envelope<String>) -> Envelope<usize> { let n = e.unpack().len(); e.repack(n) }`。
注意 len 是 UTF-8 字节数；若需求是 Unicode 标量值个数，应明确改用 chars().count()，
不能把两者混淆后宣称业务逻辑相同。

**练习 B：** 故意使用 Envelope::new 构造结果，预测哪条断言失败，再运行确认。
参考答案：partial_id 从 Some(42) 变成 None；载荷字符串仍可能正确。

**练习 C：** 不看原文件，画出“调用前 → unpack 后 → repack 后”的所有权与元信息变化。
参考答案：信封所有权进入函数；载荷取走、元信息留下；新载荷与旧元信息组合为返回信封。
原调用者不能继续使用已移动的输入。不要画成复制了两个可以独立修改的原信封。

能修改示例只是第一步。每个阶段还要有一道没有直接模板的新需求，例如改变批处理
权重、增加端口语法或修复失败后的收尾，并独立写验证。参考答案用于复盘，不能代替
自己推导。最终要从空工程构建出完整框架并通过原版业务对照，才达到本书目标。


## 维护自己的书与工程：不要只看构建命令成功

跟着本书开发时，章节会重命名、函数会移动、代码引用会调整。`mdbook build` 能生成页面，
不代表每个章节链接和标题锚点都存在。完整教程需要读者能沿着学习路线走通。

在仓库根目录运行：

```sh
mdbook build book
python3 scripts/check_book_links.py
```

第二条命令只使用 Python 标准库，会检查生成 HTML 中的本地页面、标题锚点、图片、样式表
和脚本文件。它不访问互联网，不验证外部文档是否仍然可用，也不证明代码语义与原版相同。
页面数量不是知识覆盖率；这里只把导航完整性变成可重复的检查。

默认构建目录是 `book/book`，站点前缀是 `/megflow_rebuild/`。检查别的目录时可以使用
`--root 路径 --site-path /你的前缀/`；修改 `book.toml` 中的 site-url 时也要同步这个参数。
没有 HTML 的空目录会失败，避免忘记构建却得到“零错误”。

若报“文件不存在”，检查链接的相对路径和目标文件；若报“锚点不存在”，检查目标标题
生成的 HTML id。URL 中的 `%E4...` 会先解码再比较，因此中文标题也可以校验。
代码使用 HTMLParser 读取标签，而不是用正则猜测 HTML 结构。

维护者还可以运行 `python3 scripts/test_book_links.py`。这会构造正确链接以及故意损坏
的锚点、资源路径和站点前缀，证明检查器确实能发现错误。这两条 Python 检查已加入
CI 的书籍构建之后、发布之前；本地通过不表示已经执行过远端部署。
